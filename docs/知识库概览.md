## 二、检索机制

`store.py` 实现「向量空间模型 + 关键词保底」的混合检索（RAG 思路）：

```
query_knowledge(domain, query)
  ├─ 空串           → 返回该域全部（上层枚举场景/风格/预算档依赖此行为）
  ├─ 短单 token     → 仅关键词精确匹配（向后兼容，零退化）
  └─ 多 token / 长句 → 关键词命中 ∪ 向量语义召回，按相关度排序
```

| 环节 | 实现 |
|---|---|
| 切词 | 中文**字符 unigram + bigram**，拉丁/数字整词小写（纯正则，无 jieba） |
| 向量 | TF-IDF 手写实现 + 余弦相似度（**纯标准库 math/re**，无 numpy/sklearn） |
| 索引文本 | 递归收集条目所有字符串字段（含嵌套 `substyles` 名称） |
| 混合策略 | 关键词命中**一定保留**，额外加 `0.35` 分；向量召回需 `≥0.18` |

**检索参数**（`backend/config.py`，当前为**硬编码常量，不可 env 配**）：

| 参数 | 值 |
|---|---|
| `rag_enabled` | `True` |
| `rag_keyword_boost` | `0.35` |
| `rag_min_score` | `0.18` |
| `rag_top_k` | `8` |

> `rag_enabled=False` 可一键回退到旧纯关键词行为。

## 十、观察与建议

1. **知识规模偏小** —— 55 条静态知识，覆盖「花材/风格/场景/搭配/预算/包装」六个维度，对 C 端导购场景**基本够用**，但深度有限：
   - 花材仅 16 种（实际市面常见远超这个数）
   - 养护知识（浇水/剪枝/花期延长）**完全缺失** —— 用户问「怎么养久一点」只能靠 LLM 通用知识
2. **`shop` 域是死代码** —— `_load_shops()` 恒返回空列表，`_DOMAINS` 里却保留注册。若确定不用商家智库，可清理；若将来要用，需接 `shop_profiles` 表。
3. **RAG 参数不可配** —— 4 个参数是 `@property` 硬编码，调参需改代码重建。建议改 env 可配（与项目中其他配置一致）。
4. **`proven` 域无缓存是正确的设计** —— 随用户确认/成交动态增长，注释里已说明（缓存会导致新增不可见）。
5. **扩展源导入的性价比** —— 花卉养护类知识对留客有价值，但需先解决许可确认与字段转换。建议按需分批导入，不必一次全上。
