## 4. 鉴权闭环验证（最关键，其余全依赖它）

目标：证明「换票 → 带票调用 → `user_id` 一致」三件事成立，且能稳定复现 403。

```bash
# ① 换票（X-API-Key 只能出现在服务端）
RESP=$(curl -s -X POST $BASE/auth/token -H "X-API-Key: $PKEY" \
  -H 'Content-Type: application/json' -d '{"external_user_id":"selftest_user_001"}')
TOKEN=$(echo "$RESP" | jq -r .access_token)
UID=$(echo "$RESP"   | jq -r .user_id)      # 形如 wxmini_be1ed470939b8215110d849c

# ② /auth/me 应返回 authenticated=true 且 user_id 与 ① 一致
curl -s -H "Authorization: Bearer $TOKEN" $BASE/auth/me | jq

# ③ 正向：user_id 与 JWT sub 一致 → 200
curl -s -X POST $BASE/chat -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d "{\"user_id\":\"$UID\",\"message\":\"你好\"}" | jq '{ui, session_id}'

# ④ 反向：自造 user_id → 必须 403
curl -s -w ' [%{http_code}]\n' -o /dev/null -X POST $BASE/chat -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"user_id":"my_own_id_123","message":"你好"}'

# ⑤ 反向：不带凭证 → 必须 401
curl -s -w ' [%{http_code}]\n' -o /dev/null -X POST $BASE/chat -H 'Content-Type: application/json' \
  -d "{\"user_id\":\"$UID\",\"message\":\"你好\"}"
```

**判定标准**

| 用例 | 期望 |
|---|---|
| ① 换票 | 200，`user_id` 匹配 `^<platform>_[0-9a-f]{24}$` |
| ② `/auth/me` | `authenticated=true` 且 `user_id` 与 ① 一致 |
| ③ 一致调用 | 200，返回 `session_id` |
| ④ 自造 user_id | **403** `无权访问其他用户的数据` |
| ⑤ 无凭证 | **401** `需要 Bearer 登录凭证` |
| 错误 Key | **401** `平台凭证无效，请检查 X-API-Key` |
| 匿名登录 | **403** `匿名登录已禁用…`（生产） |

> 派生算法见 `backend/auth.py:136-143`；403 判定见 `backend/auth.py:87-89`。**同一 `external_user_id` 多次换票必须得到同一个 `user_id`**（不落盘 openid，Key 轮换不影响）。

## 5. 真实对话验证

```bash
# 首轮：不带 session_id
R1=$(curl -s -X POST $BASE/chat -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d "{\"user_id\":\"$UID\",\"message\":\"我想送花给朋友，预算200左右\",\"location\":{\"lat\":22.55,\"lng\":114.06}}")
echo "$R1" | jq '{reply, ui, stage, session_id}'; SID=$(echo "$R1" | jq -r .session_id)

# 次轮：回传同一 session_id，应能引用上文（对照：不传则答不上且 session_id 变化）
curl -s -X POST $BASE/chat -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d "{\"user_id\":\"$UID\",\"session_id\":\"$SID\",\"message\":\"刚才第一个方案叫什么\"}" | jq '{reply}'

# 会话列表 / 历史消息
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/conversations?user_id=$UID" | jq
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/conversations/$SID/messages?user_id=$UID&limit=50" | jq
```

**判定标准**

- [ ] 首轮 200，耗时 3~20 s（典型 15 s）；`ui` ∈ 8 种之一且 `data` 结构与 `ui` 匹配（对照 `/ui-contract`）
- [ ] 回传 `session_id` 能引用上文；不回传则 `session_id` 变化且答不上
- [ ] 会话列表按 `updated_at DESC`；历史消息中 `role=tool` 已过滤
- [ ] 历史消息 `ui` 可被前端正确解析（见 [05 §4.2](./05-前端对接契约.md)）
- [ ] 传入他人 `session_id` 时静默新建会话（不报错），响应 `session_id` 与传入不同

## 6. 生图任务验证（创建 → 轮询 → 拿到图）

```bash
# ① 触发生图（DIY 方案定稿后自动触发，或直接要求）
R=$(curl -s -X POST $BASE/chat -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d "{\"user_id\":\"$UID\",\"session_id\":\"$SID\",\"message\":\"给我看一下预览图\"}")
echo "$R" | jq '{ui, data}'; TID=$(echo "$R" | jq -r '.data.task_id')

# ② 轮询（2 秒一次，实测约 54 秒出图，最多 45 次）
for i in $(seq 1 45); do
  S=$(curl -s -H "Authorization: Bearer $TOKEN" "$BASE/tasks/$TID")
  echo "$i $(echo "$S" | jq -r '.status')"
  [ "$(echo "$S" | jq -r .status)" != "processing" ] && break
  sleep 2
done
echo "$S" | jq -r .result_url

# ③ 校验图片可公网访问（相对路径必须拼域名）
curl -s -o /dev/null -w '%{http_code}\n' "$BASE/generated/$TID.png"     # 期望 200
```

**判定标准**

| 项 | 期望 |
|---|---|
| `ui` | `image_task`，`data.task_id` 非空、`data.poll` = `/tasks/{task_id}` |
| 轮询鉴权 | 不带 JWT → 401；带他人 JWT 查自己的任务 → `status: not_found` |
| 状态机 | `processing` → `done`（约 54 s）→ `result_url = /generated/{task_id}.png` |
| 失败态 | `failed` 带 `error`；`not_found` 表示任务不存在或归属不匹配 |
| 图片可访问 | `GET $BASE/generated/{task_id}.png` → **200** |
| 超时保护 | 前端 90 s 硬超时后停止轮询并提示重试 |

> ⚠️ 成功状态值是 **`done`** 不是 `completed`。
> ⚠️ 服务重启后遗留 `processing` 会被批量置 `failed`（`tasks.py:56-62`），这是预期行为。
> ⚠️ 百炼返回的图片是**带签名的 OSS 临时地址**，后端会立即下载落盘到 `data/generated/`。若容器 `./data` 未挂载，重启后图片全部丢失 → 轮询返回 `done` 但 URL 404。

## 7. SSE 实时流验证技巧（**不要靠反复调 LLM**）

**问题**：验证 `/api/metrics/stream` 是否推送，直觉做法是连续调几次 `/chat` 造数据。代价是每次 ~15 s、消耗 LLM 额度、污染 `calls_24h` 与 `avg_latency_24h` 统计。

**正确做法**：直接往 `call_logs` 插一行探针，SSE 每 2 s 扫 `id > last_id` 的新行（`metrics.py:153-183`），2 秒内即可看到推送，测完删掉。

```bash
# ① 开一个 SSE 监听（Header 传密钥；⚠️ ?key= 不被支持，见 §8 注）
curl -N -H "X-Dashboard-Key: $DKEY" $BASE/api/metrics/stream &
SSE_PID=$!

# ② 插探针（另一个终端）
docker exec -it flora-postgres psql -U flora -d flora_agent -c \
"INSERT INTO call_logs (user_id, platform_id, session_id, model, status, latency_ms, tool_calls, created_at)
 VALUES ('probe_selftest','wxmini','probe-session','qwen3.8-flash','success',1,0, NOW()) RETURNING id;"

# ③ 观察：2 秒内应看到一行 data:{"id":...,"user_id":"probe_selftest",...}

# ④ 清理（必做，否则污染统计）
docker exec -it flora-postgres psql -U flora -d flora_agent -c \
"DELETE FROM call_logs WHERE session_id = 'probe-session';"

kill $SSE_PID
```

**判定标准**

- [ ] 插入后 ≤ 2 s 收到一条 `data:` 行，含 `user_id=probe_selftest`
- [ ] 不再插入时不再推送（无空转刷屏）
- [ ] 断开连接后服务端退出循环（`request.is_disconnected()`，`metrics.py:162`）
- [ ] 探针已 DELETE，`SELECT count(*) FROM call_logs WHERE session_id='probe-session'` = 0

> 用同一思路可验证 `/chat/stream`：**真实调用一次即可**（不要循环打）。观察是否依次出现 `tool_call` / `text` / `card` / `done`，并确认 `done.session_id` 被保存。

## 8. 监控面板冒烟

```bash
C='%{http_code}'
curl -s -o /dev/null -w "$C\n" $BASE/dashboard/                                  # ① 期望 200（/dashboard 期望 302）
curl -s -o /dev/null -w "$C\n" $BASE/api/metrics/summary                         # ② 无密钥 → 401
curl -s -o /dev/null -w "$C\n" -H "X-Dashboard-Key: wrong" $BASE/api/metrics/summary   # ③ 错密钥 → 401
curl -s -H "X-Dashboard-Key: $DKEY" $BASE/api/metrics/summary | jq               # ④ 正确密钥 → JSON
curl -s -H "X-Dashboard-Key: $DKEY" "$BASE/api/metrics/calls?hours=24&bucket=hour" | jq '.[0]'
curl -s -H "X-Dashboard-Key: $DKEY" $BASE/api/metrics/tools | jq
# ⑤ 未配置 DASHBOARD_API_KEY 时（本地可临时清空复现）→ 503 而非 200
```

**判定标准**

| 用例 | 期望 |
|---|---|
| `/dashboard/` | **200**；`/dashboard` → 302 |
| 无密钥 | **401** `监控密钥无效` |
| 错密钥 | **401** |
| 正确密钥 | 200 + JSON（`summary` 含 `total_calls`/`calls_24h`/`errors_24h`/`avg_latency_24h`） |
| 未配 `DASHBOARD_API_KEY` | **503** `监控面板未启用…`（`metrics.py:38-39`） |

> ⚠️ **已知缺陷**：`_verify()`（`metrics.py:49-58`）只读 Header，不读 query `?key=`；而 `dashboard/app.js:266` 建 SSE 用的正是 `?key=`，浏览器 `EventSource` 又无法自定义 Header → **面板实时流当前必然 401**。支持 query 的 `require_dashboard()` 目前无任何端点引用。修复前按 §7 用带 Header 的客户端验证。

## 11. 常见失败与定位手法

| 现象 | 根因 | 定位 | 处置 |
|---|---|---|---|
| **403 无权访问其他用户的数据** | 请求体 `user_id` ≠ JWT `sub` | 比对 `/auth/token` 返回值 | 用派生值，别自造、别用 openid |
| **401 需要 Bearer 登录凭证** | 请求头缺失或前缀错 | 检查 `Authorization` | 必须是 `Bearer <token>` |
| **401 登录凭证无效或已过期** | JWT 超 30 天 | 解 JWT 看 `exp` | 重新 `/auth/token` |
| **504 处理超时** | 单轮超 180 s | `docker logs flora-agent` | 简化问题 / 改流式 |
| **500 智能体执行失败** | 未捕获异常 | `docker logs flora-agent --tail 200` | 看 traceback |
| **LLM 返回 402** | **额度/余额耗尽** | 日志与 `call_logs.error` | **充值或换 Key；重试无效** |
| **LLM 返回 429** | **QPS/TPM 限流** | 同上 | **退避重试、降并发；充值无用** |
| 生图长期 `processing` | 百炼异步任务慢 / `IMAGE_API_KEY` 未配 | `docker logs \| grep -i image` | 配 Key；前端 90 s 超时 |
| 生图 `failed` + 服务重启文案 | 重启回收（`tasks.py:56-62`） | 看 `error` 字段 | 重新生成 |
| 图 `done` 但 URL 404 | `./data` 未挂载或文件被清 | `docker exec flora-agent ls data/generated` | 挂卷、重新生成 |
| 图片裂图 | 相对路径未拼域名 | 看前端 URL | 拼 `https://api.tiaowulan.com` |
| 前端中文乱码 | `onChunkReceived` 的 ArrayBuffer 未解码 | 打日志看原始字节 | 用 [05 §3.2](./05-前端对接契约.md) 的解码器 |
| 文本翻倍 | `success` 回调重复渲染 | 断点看调用次数 | `success` 只做收尾 |
| 面板 SSE 一直 401 | `?key=` 不被 `_verify` 支持 | `curl -H "X-Dashboard-Key: ..."` 对比 | 用 Header；或修 `metrics.py` |
| `/api/metrics/*` 全 503 | 未配 `DASHBOARD_API_KEY` | `docker exec flora-agent env \| grep DASHBOARD` | 配密钥后重启 |
| 会话「聊上句忘下句」 | 未回传 `session_id` | 抓包看请求体 | 保存并回传 |
| 店铺信息答不出 | 字段映射未覆盖 | 查 `mapping_store` active 映射 | 补映射（见小程序待办清单 §4） |
| 平台数据乱码（如 `30-60鍒嗛挓`） | **平台库写入时编码错误**，非本服务问题 | 直连 MySQL 查源行 | 平台方修数据 |

### 11.1 真实案例：LLM 402 vs 429

两者都表现为「智能体答非所问或直接说模型调用出错」，但**处置完全相反**，误判会浪费大量时间：

- **402（额度耗尽）**：账户余额或包月额度用完。特征是**所有请求**稳定失败、日志出现 `402` / `Payment Required` / `InsufficientBalance`。此时**重试、降并发都无效**，必须充值或更换 `LLM_API_KEY`。
- **429（限流）**：QPS/TPM 超限。特征是**间歇性**失败、并发高时更频繁、日志出现 `429` / `Rate limit` / `Throttling`。此时**充值无效**，应做指数退避重试、降低并发或申请提额。

> 两者都不会变成 HTTP 5xx：`agent.run()` 内部捕获后写进 `reply`（`agent.py:186-189`），HTTP 仍是 200。判断依据只有**日志与 `call_logs.error`**，联调时务必先看监控面板的 `errors_24h` 与 `avg_latency_24h`。
