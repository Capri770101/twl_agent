## 1. 背景与问题

平台方已有微信小程序等前端，但缺少「花艺领域的对话式智能推荐与方案设计能力」。自建模型与管线成本高、周期长。本项目以**后端即服务**的方式，把智能体能力通过 HTTP API 对外提供，前端以最小改造接入，避免每个端重复造轮子。

## 2. 目标与非目标

### 2.1 目标（In Scope）

1. 提供统一的花艺对话入口（`/chat`），支持多轮、意图识别、工具调用。
2. 提供 DIY 花艺方案设计、AI 生图、电子贺卡能力。
3. 支持多平台接入：接入方用平台密钥为用户换 JWT，互不干扰。
4. 支持「店铺锁定」：用户从某店铺进入时，推荐/查询均限定本店。
5. 提供内置调用监控面板，覆盖量、延迟、错误、工具分布与实时流。
6. 平台商品/店铺/订单数据**只读**实时查询，智能体不落地、不直接下单。

### 2.2 非目标（Out of Scope）

1. **不直接下单**：下单走小程序现有结算页（见架构决策 #2）。
2. **不做小程序内置**：小程序提审成本高，本项目只做后端 API。
3. **不镜像平台数据**：不建本地商品/订单库，避免双写与一致性风险。
4. **不持有用户身份**：终端用户认证由宿主完成。

## 3. 用户故事与功能需求

### 3.1 对话核心（FR-01）

- **作为** C 端用户，**我希望**用自然语言问花/挑花/定制，**以便**获得专业建议。
- 智能体需识别意图 `buying/qa/chitchat/design/other`，并在合适时机调用 `respond_to_user` 结束本轮。
- 接受标准：多轮上下文连续；意图判定依据「用户想干什么」而非是否调工具。

### 3.2 花艺知识问答（FR-02）

- **作为** 用户，**我想**问花期/养护/寓意/送什么花好，**以便**得到准确知识。
- 工具：`retrieve_knowledge` 检索知识库。
- 接受标准：回答有依据、不编造花材属性。

### 3.3 DIY 方案设计（FR-03）

- **作为** 用户，**我想**描述预算/对象/风格，**得到**一份结构化花束方案。
- 工具：`generate_diy_plan` / `revise_diy_plan`（带 version + parent_id 可追溯）。
- 接受标准：方案含主花/配材/配比/色彩/包装/寓意/预算估算；改版继承店铺限定。

### 3.4 AI 生图（FR-04）

- **作为** 用户，**我想**看到方案效果图，**以便**下单前预览。
- 工具：`generate_effect_image` → `GET /tasks/{task_id}` 轮询；provider = qwen（`qwen-image-3.0` 原生接口）。
- 接受标准：返回带签名时效的 OSS 地址在后端**立即下载转存**；前端拿到的 `image_url` 稳定可访问。

### 3.5 电子贺卡（FR-05）

- **作为** 用户，**下单成功后**希望收到带祝福语的电子贺卡。
- 工具：`suggest_greetings` / `render_greeting_card`（5 套模板，PIL 合成 900×1200）。
- 接受标准：落款 `sender` 用用户昵称/自选文案（非 raw user_id）；底部水印固定「以花传情」。

### 3.6 店铺/商品查询（FR-06）

- **作为** 用户，**我想**查某店铺在售方案/基本信息，**以便**挑选。
- 工具：`platform_db_query_entity(source_id, entity=plan|shop|order|user)`。
- 接受标准：只读；会话锁定店铺时结果自动限定本店；无 active 映射时拒绝执行。

### 3.7 多平台接入与鉴权（FR-07）

- **作为** 接入方后端，**我想**用平台密钥为用户换 token，**以便**隔离各端用户。
- 接口：`POST /auth/token`（X-API-Key + external_user_id → JWT）；可选 `POST /auth/wx-login`。
- 接受标准：`user_id` = platform_id + external_user_id 哈希派生；`/chat` 的 user_id 必须等于派生值（否则 403）。

### 3.8 监控可观测（FR-08）

- **作为** 运营/研发，**我想**看调用量、平台、工具、延迟、错误与实时流。
- 接口：`GET /api/metrics/summary|calls|platforms|tools|stream`，`DASHBOARD_API_KEY` 保护。
- 接受标准：真实 `/chat` 调用后指标有数据；SSE 实时流可推送新行。

## 4. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 单轮对话 P95 < 20s（qwen3.8-flash 带推理，实测约 15s）；生图约 50s 异步返回 |
| 可用性 | 四容器 `restart: unless-stopped`；agent 健康检查 `/health` |
| 安全 | 密钥三层分离；平台库只读；JWT HS256 ≥ 32 位；生产强制 PostgreSQL + 明确 CORS（见 [docs/10-安全与合规.md](./10-安全与合规.md)） |
| 可观测 | 监控埋点对主链路 best-effort，异常只 warning 绝不阻断业务 |
| 兼容性 | 流式输出兼容小程序（`wx.request({enableChunked:true})` + `onChunkReceived`），非 EventSource |
| 可维护 | 工具注册靠 `agent/__init__.py` 导入触发；标准分层（api/services/repositories/models/schemas） |

## 5. 约束与依赖

- **外部依赖**：阿里云百炼 DashScope（LLM + 生图）、平台方只读 MySQL 连接串、PostgreSQL 16。
- **部署约束**：代码 `COPY . .` 烤进镜像，改代码必须 `--build agent`；nginx.conf 为 bind mount，改完 `nginx -s reload`。
- **合规约束**：平台库只读，绝不写订单；生图 OSS 地址须在服务端转存，不外泄临时签名。

## 6. 验收标准（概要）

完整用例见 [docs/09-测试与验收.md](./09-测试与验收.md)。关键验收点：

1. 真实 `/chat` 多轮对话成功，意图识别正确。
2. DIY → 生图 → 贺卡链路打通，`/tasks/{id}` 轮询拿到稳定 `image_url`。
3. 店铺锁定场景下推荐/查询均限定本店。
4. 平台只读：无法通过智能体写入平台库。
5. 监控面板数据真实、SSE 实时流可用。
6. 安全：错误响应不泄露内部细节（见已知问题 K-1）。
