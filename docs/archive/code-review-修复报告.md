## 三、关键修复细节

### 1. 端到端集成测试（一切重构的前置）

此前**没有任何测试真正跑过完整 `run()`** —— `test_stream_hang.py` 把 `run` 本身
mock 掉了，其余 47 个文件全是纯函数单测。等于蒙着眼睛改 630 行核心逻辑。

新增 `tests/test_run_e2e.py`：mock 掉存储层与 LLM，但**让主循环真跑**，
从用户消息一路走到 `ChatResponse`，断言最终 `ui / data / reply`。四个场景：

- 纯文字回复（happy path）
- DIY 出卡（多轮 + 工具执行）
- **护栏拦截真的生效**（断言 LLM 被调 ≥ 2 次）
- 清理链端到端（危险标签 / 工具名 / 分隔线都被处理）

这个测试**当场就抓出了两次问题**（见第四节）。

### 2. 清理链 → 显式管道

**修复前**：8 个清理/兜底函数硬编码散在 `run()` 末尾，顺序语义只存在于代码行先后。

**修复后**：一张阶段表 —— 顺序一眼可见、每步带 `why`（写清「为什么必须在这个位置」）、
条件步骤用 `enabled` 表达。`run()` 里那 10 行缩成一行调用。

```python
_CLEANUP_PIPELINE: tuple[_CleanupStep, ...] = (
    _CleanupStep('strip_separator_lines', ..., '先删独立分隔线：放最前，避免被后续步骤当正文'),
    _CleanupStep('strip_internal_leak', ..., '隐私兜底。**必须早于 XSS 转义**，否则...'),
    _CleanupStep('neutralize_dangerous_tags', ..., 'XSS 兜底，放在泄漏清理之后'),
    _CleanupStep('ensure_card_summary', ..., needs=('reply', 'ui', 'data')),
    _CleanupStep('ensure_non_empty_reply', ..., '⚠️ 脱敏可能清空正文，必须紧跟其后'),
    _CleanupStep('demo_trade_note', ..., enabled=lambda: not _shop_entity_enabled()),
    _CleanupStep('finalize_image_claim', ..., needs=('reply', 'tool_log')),
    _CleanupStep('finalize_reasoning_leak', ..., '⚠️ 整段替换，必须最后'),
)
```

新增 `tests/test_cleanup_pipeline.py` 锁住顺序 + 要求每步都有 `why`。

### 3. 护栏拦截 → `_check_guards()`

**修复前**：4 项护栏在 `run()` 里内联了**两套共 8 处**（`respond_to_user` 分支 +
零工具调用分支），约 80 行；4 个计数器（`_xxx_nudge_left`）散在局部变量里与拦截点交错。

**修复后**：`_GuardBudget` 收拢状态 + `_check_guards()` 统一判定，两条路径各缩成一次调用。

⚠️ **保留了「两条路径都要拦」这一关键设计** —— 线上实测的护栏漏洞正出在
「模型零工具调用直接回文字」那条路上（4.5 秒回文字，护栏形同虚设还谎称有卡片）。

### 4. 工具与 UI 元数据集中

**修复前**：`_CARD_UIS`(282 行) / `_CARD_TOOLS` / `_TERMINAL_TOOLS` / `_DEFERRED_TOOLS`(710+ 行)
/ UI→Action 映射（写在 `run()` 里）**分散在 5 处** —— 新增一个工具要改 5~6 个地方，
且没有任何一处能看全「现有工具各是什么角色」。

⚠️ 最危险的是**静默退化**：新 UI 忘了登记映射 → 前端只收到 `SHOW_TEXT`，
卡片消失且**不报错**。

**修复后**：全部集中到 `agent/tools_meta.py`，附「新增工具要改哪几处」的 7 步清单。
`agent.py` 用下划线别名导入，既不动内部引用，也保持
`from agent.agent import _DEFERRED_TOOLS` 这类既有测试照常可用。

### 5. 工具异常脱敏

```python
# 修复前：异常 repr 直接进上下文，可能带内部路径 / 参数 / 堆栈片段
results[i] = (f'工具执行失败: {item}', 'error')

# 修复后：只给「哪类失败 + 该怎么办」，原始异常仍完整落服务端日志
results[i] = (_tool_error_result(tool_calls[i]['name'], item), 'error')
```

### 6. session flag 常量化（顺带查出一个真隐患）

25 处字面量收进常量表。**顺带确认了 review 说的「补丁痕迹」确有其事**：

`img_optout` 的值**不是** `image_optout` —— 它与 `prefix='image_'` 前缀不同，
`clear_session_flags(prefix='image_')` **清不掉它**，所以代码里必须再单独清一次。

⚠️ **有意不改名**：flag 存在**会话行**里，改名会让存量会话的标记静默失效
（最坏情况：用户明确拒绝过生图，却被再问一次）。要改名请先写数据迁移。

### 7. prompt 缓存加 mtime 失效

`_RAW_CACHE` 从纯进程级字典改为 `(mtime, 内容)`，改 `prompts/*.md` 后**无需重启**即生效；
同时清空 `_PROMPT_CACHE`（拼接模板依赖原文，原先这个依赖没被体现出来）。

## 四、集成测试带来的两个额外收获

写测试时摸到了两处**真实契约**（都是靠这个测试才发现，之前文档里没有）：

1. **`run()` 有两条 LLM 路径**：传了 `on_event` 走流式 `_stream_llm`（**生产 SSE 的真实路径**），
   没传则走非流式 `call_llm`（`/chat` 同步接口）。测试必须显式传 `on_event` 才覆盖生产路径。
2. **`execute_tool` 返回 `(result, status)` 二元组**，不是裸结果字符串。

## 五、未做项与理由

**不做的原因和「做」同样重要** —— 避免留下「以后要补」的模糊印象。

### `tools.py`（1915 行）未拆

理由：
1. 它是本项目**改动最频繁**的文件，拆分会产生大量 import 迁移；
2. **当前集成测试只覆盖 `run()` 主链路，对工具内部行为没有端到端保护** ——
   拆错了不会立刻被发现；
3. 收益是「未来开发效率」，而当前业务优先级不在这。

**建议拆法**（等集成测试覆盖到工具层之后再动）：按 `平台查询 / DIY 设计 /
知识检索 / 贺卡` 四个域拆，每域保留一个 `register` 入口。

### 关键词表未搬家 / 未配置化

理由：被**上百处引用**，搬家是纯风险、不带来行为改善；而「配置驱动」需要先定
「谁有权改、改了如何生效（热更新还是重启）」—— 那是产品决策，不是重构。
已用「总览 + 重叠说明」解决排查痛点。

### `run()` 未继续拆（仍 296 行）

理由：剩余职责（会话管理 / 需求累积 / 主循环调度 / 出参组装）**彼此强耦合于循环控制流**，
硬拆会把 `continue` / `break` 语义打散、反而更难读。
**建议方向**：若继续，应把主循环抽成**显式状态机**（大改），前置条件同样是集成测试覆盖更全。

### `respond_args = None` 丢信号未改

review 认为是缺陷，但这是**有意取舍**：纠正后重答时，上一轮的结构化信号
（`confirmation` / `image` / `missing`）本就**不该复用** —— 那正是违规那一轮的结论，
复用反而会让违规结论生效。
