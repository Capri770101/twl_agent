# 开发与发布流程

更新：2026-10-11。源码版本与部署版本分开记录，服务器是否为 Git 工作树以实际检查为准。

## 日常改动循环（防行为漂移）

改智能体**行为**（prompt / 工具 / 路由 / ReAct / 知识库）时走此循环，不跳步。
纯文档/typo 小改可跳过 2、4。

### ① 定目标（一句话）

写清楚：改什么 + 怎么算成功。
例：*"qa 路线回答'怎么养玫瑰'必须包含浇水频率；成功 = 新增 3 条 eval 全过且旧 12 条不掉分"*。

### ② 冻基准（改之前）

```bash
python -m pytest tests/ -q          # 必须先全绿；不绿先修再谈改动
python scripts/validate_eval_set.py
```

有真实模型评测条件时，按 [EVALUATION](EVALUATION.md) 跑一遍场景集，把**分数/通过数记在 PR 或提交说明里**。没跑过分的改动 = 盲改。

### ③ 一刀

一次提交只做一件事：**改行为** 或 **做重构**，不混。
prompt 变更单独提交（方便单独回滚）。

### ④ 验证（改之后）

```bash
python -m pytest tests/ -q
python scripts/validate_eval_set.py
python scripts/validate_knowledge.py   # 动过知识库才跑
git diff --check
```

有基准分时：新分数 **≥ 基准** 才算过；掉了就回滚或修，不许"先合了再说"。

### ⑤ 提交

- message 写**为什么改**，不只写改了什么
- 行为变更在 CHANGELOG 记一行
- 大改动（拆文件、改 ReAct 循环）拆成多个小 PR，每个都走完本循环

### 禁止事项

| 反模式 | 后果 |
|--------|------|
| 没冻基准就开改 | 无法区分"变好"和"漂移" |
| 一个提交混重构+行为 | 出问题无法二分定位 |
| AI 说"应该没问题"但没贴验证输出 | 空口保证不算验证 |
| 连续多刀不提交不验证 | 补丁叠补丁，回到 vibe coding |

## 与 AI 协作的规矩

1. **一个会话只做①里的一个目标**；中途想到别的，记 TODO 另开会话
2. **先要计划再动手**：让 AI 先列"改哪些文件、怎么验证、有什么风险"，确认后再执行
3. **强制贴证据**：要求 AI 改完必须贴 pytest 输出和评测结果，不接受"应该没问题"
4. **大动手术先让 AI 自查**：改 `agent.py` / `orchestration/executor.py` 前，先让 AI 列风险清单和回滚方式
5. AI 生成的代码同样走本循环，不豁免

## 交付流程

1. 核对工作区、目标分支与远端提交；确定交付是开发快照还是正式发布。
2. 更新 CHANGELOG、DELIVERY、配置模板及相关 API 文档；不把未验证能力写成已发布。
3. 跑 pytest、评测集/知识库校验、文档链接检查和 `git diff --check`。
4. 将确认过的源码与文档提交；需要时推送指定分支。真实配置、证书、运行数据不提交。
5. 从最终提交导出源码包，另记录完整 commit 与 SHA-256；GitHub 下载也要指定该提交，不能只说“main 最新”。
6. 私密配置和必要数据独立交接，见 [CONFIGURATION](CONFIGURATION.md)。

## 部署流程

- 先部署独立测试环境，进行真实模型、数据库、业务接口与宿主验收。
- 备份旧镜像、数据库、生成文件和配置；记录实际 Compose 项目名/卷名。
- 服务器是 Git 工作树时检出明确提交；不是时解压该提交的完整源码包。不要以零散 scp 文件覆盖替代可追溯发布。
- 按 [部署手册](07-部署手册.md) 构建；代码变更重新构建镜像，环境变量变更 recreate 容器。
- 客户服务先部署向后兼容的 agent/H5 后端，再发 H5，开关保持关闭至真实验收完成。
- 发布记录包含最终 agent/H5 commit、版本号、镜像 ID/摘要、包 SHA-256、配置项名称、备份路径、部署时间与验收报告。
- 正式验收通过后才提升运行版本与正式标签；`releases/v1.4.0/` 目录本身不构成正式发布。

## 回滚

关闭新能力 → 恢复已记录镜像/源码和兼容配置 → 验证健康及关键链路。保留新增表和业务运行数据。迁移目录时保持原卷关联；不用未经核实的全库恢复覆盖发布后的新数据。
