# 开发与发布流程

更新：2026-09-29。源码版本与部署版本分开记录，服务器是否为 Git 工作树以实际检查为准。

## 交付流程

1. 核对工作区、目标分支与远端提交；确定交付是开发快照还是正式发布。
2. 更新 CHANGELOG、DELIVERY、配置模板及相关 API 文档；不把未验证能力写成已发布。
3. 跑 pytest、评测集/知识库校验、文档链接检查和 `git diff --check`。
4. 将确认过的源码与文档提交；需要时推送指定分支。真实配置、证书、运行数据不提交。
5. 从最终提交导出源码包，另记录完整 commit 与 SHA-256；GitHub 下载也要指定该提交，不能只说“main 最新”。
6. 私密配置和必要数据独立交接，见 [CONFIGURATION](CONFIGURATION.md)。

## 部署流程

- 先部署独立测试环境，进行真实模型、数据库、业务接口与宿主验收。
- 备份旧镜像、数据库、生成文件和配置；记录实际 Compose 项目名/卷名。
- 服务器是 Git 工作树时检出明确提交；不是时解压该提交的完整源码包。不要以零散 scp 文件覆盖替代可追溯发布。
- 按 [部署手册](07-部署手册.md) 构建；代码变更重新构建镜像，环境变量变更 recreate 容器。
- 客户服务先部署向后兼容的 agent/H5 后端，再发 H5，开关保持关闭至真实验收完成。
- 发布记录包含最终 agent/H5 commit、版本号、镜像 ID/摘要、包 SHA-256、配置项名称、备份路径、部署时间与验收报告。
- 正式验收通过后才提升运行版本与正式标签；`releases/v1.4.0/` 目录本身不构成正式发布。

## 回滚

关闭新能力 → 恢复已记录镜像/源码和兼容配置 → 验证健康及关键链路。保留新增表和业务运行数据。迁移目录时保持原卷关联；不用未经核实的全库恢复覆盖发布后的新数据。
