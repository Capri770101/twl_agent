## 1. 监控总览

| 维度 | 来源 | 查看方式 |
|---|---|---|
| 调用量 / 平台 / 工具分布 / 延迟 / 错误率 | `call_logs` + `tool_call_logs` 表 | 监控面板 `https://api.tiaowulan.com/dashboard/` |
| 实时流（新调用逐行推送） | SSE `/api/metrics/stream` | 面板内实时 Feed |
| 原始指标接口 | `backend/routers/metrics.py` | `GET /api/metrics/{summary,calls,platforms,tools}` |
| 服务存活 | agent 健康检查 `/health` | `curl https://localhost/health` |
| 容器状态 | compose | `docker compose ps` |

面板登录用 `DASHBOARD_API_KEY`（仅存 `sessionStorage`）。未配该密钥时 `/api/metrics` 一律 `503`；无 key / 错 key 返回 `401`。

## 2. 指标采集原理

- **埋点层**：`backend/observability.py` 为 best-effort——任何异常只 `warning` 绝不阻断主链路；用 `ContextVar` + 显式 `cid` 兜底（SSE 跨请求场景）。
- **落库**：`backend/db.py` 的 `call_logs` / `tool_call_logs` 由 `init_db` 以 `IF NOT EXISTS` 自动建表，无需手动迁移。
- **埋点位置**：`chat.py` 入口 / 出口 / 异常分支。工具分布取自 `arun` 返回的 `tool_calls`（避开 `run()` 线程池导致 contextvar 跨线程失效），对 `agent.py` 零侵入。
- **归因**：JWT 携带 `platform` 字段仅用于 `call_logs.platform_id` 归因，不参与鉴权。

## 3. 健康检查与告警

| 检查项 | 命令 | 正常 | 异常处理 |
|---|---|---|---|
| 服务存活 | `curl -fsS https://localhost/health` | `ok` | 看 agent 日志；必要时 `docker compose restart agent` |
| 容器健康 | `docker compose ps` | 4 容器 `healthy` | 重启对应服务；502 先 `docker restart flora-nginx` |
| 指标有数据 | 面板 summary 非空 | 有调用记录 | 检查 observability 是否抛异常（只 warning） |
| 生图队列 | `GET /tasks/{id}` | `done`/`failed` | 查 `image_tasks` 表与百炼配额 |
| TLS 证书 | `openssl x509 -enddate -noout -in deploy/certs/fullchain.pem` | 未过期 | 阿里云重新下载覆盖 → `docker restart flora-nginx` |

> 告警建议（自建）：对 `call_logs` 中 `status=error` 占比 > 5% 或 P95 延迟 > 30s 触发告警；对 402/429 统计 LLM 配额耗尽。

## 4. 日常运维操作

### 4.1 看日志

```bash
docker compose logs -f --tail=200 agent      # 主服务
docker compose logs -f --tail=100 nginx       # 反代
docker exec -e PYTHONPATH=/app flora-agent python /tmp/x.py   # 容器内排障脚本
```

### 4.2 重启 / 重建

```bash
docker compose restart agent                  # 仅配置变更（无代码改动）
docker compose --profile nginx up -d --build agent   # 改了代码必须 --build
docker exec flora-nginx nginx -s reload       # 仅改 nginx.conf（bind mount）
```

### 4.3 跨网络部署兜底（GitHub 不可达时）

沙箱/服务器偶尔 `Failed to connect to github.com port 443`。兜底 scp 直传 + 服务器重建，绕开 GitHub：

```bash
# 本地（Git Bash，源路径必须写 C:/ 不能写 /c/）
scp "C:/Users/Capri/Desktop/flora_agent_package/<路径>/<文件>" \
    <REDACTED_HOST>:/opt/flora_agent_package/<同路径>/
# 服务器重建对应服务
ssh -o StrictHostKeyChecking=accept-new <REDACTED_HOST> \
    "cd /opt/flora_agent_package && docker compose --profile nginx up -d --build agent"
# 收尾：本地补 git push；服务器丢弃 scp 改动后对齐
ssh <REDACTED_HOST> "cd /opt/flora_agent_package && git checkout -- <改动路径> && git fetch && git merge --ff-only origin/main"
```

> 服务器工作树是权威版（曾比本地多 9 个改动）。判改动用 `git diff --stat HEAD`，别用 `git status | head`（会截断误判）。

## 5. 故障排查手册（按症状）

| 症状 | 可能原因 | 排查 / 修复 |
|---|---|---|
| 对话返回 402 | 百炼额度耗尽（旧为 hy 免费额度耗尽） | 确认已开后付费；`docker compose restart agent`；查 `model=qwen3.8-flash` 日志 |
| 对话返回 429 | 限流 | 降低并发；确认后付费生效；重启 agent |
| 回答极慢（>60s） | LLM 异常回落 / 思考模型 | 确认直连 qwen3.8-flash 未回落 hy；必要时 `enable_thinking:false` 或换非思考型号 |
| 答非所问 | 跨厂商 fallback 风格跳变 | 清空 `HY_API_KEY` 走纯 Qwen |
| 生图 404 | 走了 OpenAI 兼容接口 | 确认 `IMAGE_PROVIDER=qwen` 走原生 `multimodal-generation`；尺寸 `"768*1024"` |
| 生图拿到失效 URL | OSS 签名过期 | 确认后端已「立即下载转存」（代码已处理） |
| 监控 503 | 未配 `DASHBOARD_API_KEY` | 填值 → `docker compose restart agent` |
| 监控 SSE 不推 | 见 K-2 | 见第 7 节 |
| 502 | nginx 未感知 agent 重建 | `docker restart flora-nginx` |
| 店铺查询无数据 | mapping 未激活 / 字段白名单缺失 | 激活 `platform_db_query_entity` 对应 mapping；确认含标准 `shop_id` 列 |

## 6. 密钥与证书生命周期

- **`JWT_SECRET` / `PLATFORM_API_KEYS` / `DASHBOARD_API_KEY`** 三层分离，互不复用；任一泄露不牵连其它。建议均 `openssl rand -hex 32` 生成。
- **TLS 证书**：阿里云免费证书 3 个月有效期。到期提醒：阿里云证书 **2026-12-01**、服务器 **2026-10-24**。到期前重新申请下载覆盖 `deploy/certs/`，再 `docker restart flora-nginx`。
- **轮换 `DASHBOARD_API_KEY`**：改 `.env` → `docker compose restart agent`（无需重建）。

## 7. 已知问题 / 待修项（K-系列）

> K-1 / K-2 / K-3 已于 commit `48a84fb` 全部修复并验证（见下方标注）。保留此处作为归档与回归参考。

### K-1（中危·安全）`agent.py` 异常信息回显给用户 ✅ 已修复（`48a84fb`）
- **位置**：`agent/agent.py` ReAct 主循环 `call_llm` 异常分支。
- **风险**：泄露内部细节（模型 endpoint、密钥前缀、堆栈片段），属信息泄露。
- **修复**：LLM 调用失败时不再把原始异常回显给用户，改为安全兜底文案「抱歉，我这边服务暂时开小差了，请稍后再试一次～」，原始异常仅 `logger.exception` 落服务端日志。

### K-2（中危·功能）监控 SSE `?key=` 校验缺失导致实时流 401 ✅ 已修复（`48a84fb`）
- **位置**：`backend/routers/metrics.py` 的 `_verify`（SSE `/stream` 使用的同步校验函数）。
- **风险**：dashboard 前端用 `EventSource`（浏览器不允许自定义 header）只能走 `?key=`，因此 SSE 实时流会 401，面板「实时流」实际不可用。
- **修复**：`_verify` 同步支持 header（`X-Dashboard-Key` / `Bearer`）与 query `?key=` 两种来源（与 `require_dashboard`、summary/calls 等接口保持一致）。线上验证：正确 `?key=` → 200、错误 key → 401。

### K-3（低危·数据）店铺基础信息 mapping 不完整 ✅ 已修复（`48a84fb`）
- **位置**：`platform_db_query_entity` 的 `shop` 实体 active mapping（数据驱动，存于内部 PG `mapping_drafts`）。修复前仅映射 8 个字段。
- **风险**：前端查店铺基础信息时拿不全（营业时间、状态、起送价、配送费等）。
- **修复**：新增幂等脚本 `scripts/patch_shop_mapping.py`，为 active 映射的 shop 实体补齐 `business_hours` / `status` / `delivery_time` / `delivery_fee` / `min_order_price` 五个字段，并对 `delivery_fee` / `min_order_price`（平台以「分」存储）补 `cents_to_yuan` 转换（与 `plan.price` 一致）。已在生产 `s001` 执行，映射升到版本 3，线上查询已返回上述字段。

### F-1~F-4（中危·功能）智能体读不出店铺营业时间 / 营业状态 ✅ 已修复（`45c55f7`）
- **现象**：平台库 `shops` 表有 `business_hours` / `status` / `delivery_time` / `delivery_fee` / `min_order_price`，且 K-3 已把这些字段补进 mapping（**数据层可查**）；但用户问「几点关门」「现在开门吗」「多久送到」时，智能体答不上来或凭常识瞎编。
- **根因（四层叠加，缺一不可）**：
  - **F-1 工具 schema 没列字段**：`agent/data_tools.py` 的 `platform_db_query_entity` description 只写「按 active 映射只读查询标准业务实体」，未列任何具体字段 → LLM 不知道能查营业时间。
  - **F-2 prompt 无场景引导**：system prompt 场景段只有买花束 / DIY / 知识 / 改方案 / 查订单 / 未接入，**没有「营业 / 配送」场景**。
  - **F-3 无时间感知**：prompt 未注入当前时间 → 即便拿到 `business_hours='07:00-22:00'`，LLM 也算不出「现在是否营业」。
  - **F-4 店铺锁定规则误伤**：`agent.py` 店铺锁定段写「不要再调用 `entity="shop"` 去"选店铺"」，本意是禁止推荐别家，却连带禁掉了「查本店营业信息」这个正当需求。
- **修复**：
  - F-1 工具 description 列出 shop 可用字段与可回答的问题样例，并明确「缺字段如实说查不到」「不要罗列别家店，但查本店营业配送不受限」。
  - F-2 新增「场景6：用户问店铺营业 / 配送信息」，含字段读取、营业时段比对、静态 `status` 与时段冲突时的处置；原场景 6/7 顺延为 7/8（已验证编号 1–8 连续无重复）。
  - F-3 新增 `_now_context()`，在 system prompt「当前时间」段注入日期 + 星期 + 时刻。
  - F-4 店铺锁定规则改为「禁止推荐 / 跳转别家店，但允许查本店营业与配送信息」。
- **踩坑**：`_now_context()` 初版用 `datetime.now()` 取容器本地时间，而容器默认 **UTC**，比北京时间慢 8 小时（线上实测注入成 `08:14` 而实际 `16:14`）→ 拿它比对营业时段会全错。已改为显式 `timezone(timedelta(hours=8))` 取北京时间，**不依赖容器 TZ**。
- **验证**：生产容器内 `call_llm` 实测「你们几点关门？」「现在还开门吗？」「多久能送到？起送价多少？」三问，LLM 均主动调用 `platform_db_query_entity(source_id="s001", entity="shop")`。
- **跟进**：G-1 已把「是否营业」改为实时推算（见下），该残留风险随之消除。

### G-1（功能）营业状态实时推算 ✅ 已实现（`6bd32ec`）
- **背景**：平台库 `status` 是静态字段，不反映此刻是否真在营业。只读架构（ADR-1）下不能回写平台库把 `status` 同步成实时值。
- **方案**：在 `query_external_entity` 展示层按当前北京时间**实时推算**，为含 `business_hours` 的行补两个派生字段（只读派生，不写库）：
  - `is_open_now`：`true` / `false` / `null`
  - `open_status_text`：`营业中` / `已打烊` / `未知（…）`
- **解析能力**：单段 `07:00-22:00`、24 小时 `00:00-24:00`、跨天 `18:00-次日02:00`、多段 `09:00-12:00,14:00-18:00`、波浪线 `9:00~18:00`。**解析不出任何区间时返回 `null`（未知）而非 `false`**——宁可未知，也不能把「看不懂」说成「已打烊」。
- **时区**：显式按北京时间 UTC+8 推算，不依赖容器 TZ（容器默认 UTC，见 F-3 踩坑）。
- **上层约定**：LLM 直接读 `open_status_text`、**不自己比对时间**（prompt 场景6 与工具描述均已同步改）；平台静态 `status` 与推算冲突时以推算为准，并提示「以店铺实际为准」。
- **验证**：20 条固定时刻断言全绿；生产实测 16:49 → `营业中`；全天抽样 06:30 未开 / 07:00 开 / 21:59 开 / 22:00 打烊 / 23:30 打烊；端到端多轮实测 LLM 正确组织出「营业中 + 时段 + 配送 + 以店铺实际为准」的答复。

### G-2（高危·功能）店铺查询工具因 Decimal 直接崩溃 ✅ 已修复（`8638655`）
- **位置**：`backend/data_gateway/mapper.py::tool_result`（所有外部数据工具返回值的**统一序列化出口**）。
- **现象**：`json.dumps` 抛 `TypeError: Object of type Decimal is not JSON serializable` → `platform_db_query_entity` 整个调用失败，LLM 拿不到任何店铺数据。
- **根因**：平台库 MySQL 的 `rating` 是 DECIMAL，驱动返回 `decimal.Decimal`；`tool_result` 没有 `default` 兜底。
- **影响范围**：**查店铺功能此前一直是坏的**——不只是读不到营业时间，而是任何 `entity=shop` 查询都会失败。此前 F 系列的端到端只验证到「LLM 决定调用」、未真实执行工具，因此漏网。
- **修复**：新增 `_json_default` 兜底——Decimal 转 float、datetime/date/time 转 ISO 串、timedelta 转秒、bytes 按 UTF-8 或 hex、其余转 str。
- **教训**：端到端验证必须跑到「工具真实执行 + 结果回填 + 最终答复」。只看到 LLM 决定调用**不能算通过**。
