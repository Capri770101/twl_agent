## 3. ReAct 引擎执行流程

### 3.1 三个入口的关系

```
POST /chat                   POST /chat/stream (SSE)
   │                                │
   ▼                                ▼
arun (agent.py:107)          arun_stream (agent.py:112)
   │ run_in_executor+asyncio.run      │ Queue + _run 任务 + run_in_executor
   ▼                                  ▼
run (agent.py:151)           run(..., on_event=_on_event)
   唯一真实实现：同步主循环（独立事件循环）
```

### 3.2 为什么 `run()` 必须在线程池执行

1. 存储层是**同步阻塞**的：`backend/storage/db.py` 用 psycopg3 同步连接（`get_conn()` 线程局部复用，`db.py:115`），`transaction()` 是同步上下文管理器，整条 `run()` 链路都是同步代码。
2. 直接 await 会**阻塞事件循环**：一个 30s+ 的智能体会把整进程其它请求卡死。
3. 故 `arun/arun_stream` 统一用 `loop.run_in_executor(None, lambda: asyncio.run(self.run(...)))`，**每次调用在 worker 线程新建事件循环**。

### 3.3 ContextVar 跨线程失效的坑（必读）

`backend/observability.py:26` 用 `ContextVar` 保存请求级 `call_log_id`。但 `run()` 跑在 executor 线程、且内部是另一个事件循环，`ContextVar` **不会自动带入**，`asyncio.run()` 新建的循环里更读不到外层值。

结论：**不要指望线程内代码读 `_call_id`，一律显式传 `cid`。**

```python
# backend/routers/chat.py:66 入口建 call_log 拿 id；chat.py:93-95 出口显式传 cid
_call_id = record_call_start(req.user_id, _platform, req.session_id, settings.LLM_MODEL)
...
record_call_end('success', _latency, tool_calls=len(_tool_calls), cid=_call_id)
for _tc in _tool_calls:
    record_tool_call(getattr(_tc,'name','?'), getattr(_tc,'status','unknown'), cid=_call_id)
```

`record_call_end/record_tool_call` 仅在 `cid is None` 时才回退 ContextVar（`observability.py:72`、`:97`）。同理**agent 层不要写埋点**——它在线程里，关联不到请求。

### 3.4 `on_event` 回调机制（SSE）

```python
# agent.py:126-133
def _on_event(evt: dict) -> None:
    loop.call_soon_threadsafe(queue.put_nowait, evt)   # 线程安全投递
```

事件类型：`tool_call`（工具名 + ok/error，`agent.py:207`）、`text`、`card`、`done`（带 `session_id`）、`error`。
`text` 是**准流式**：`run()` 已生成完整回复，`agent.py:232-242` 才按 `。！？\n` 或每 20 字切片、`sleep(0.03)` 逐块推出；底层 LLM 仍是 `stream=False`（`llm.py:117` 支持但 `run()` 未传），故首字延迟 ≈ LLM 整段生成时间。真 token 级流式需改 `run()` 用 `call_llm_stream` 并处理 ReAct 工具轮次与流式的冲突。

### 3.5 主循环与后处理

```python
# agent.py:182-216（节选）
for turn in range(1, settings.max_iterations + 1):
    resp = call_llm(messages, tools=to_openai_tools())
    tool_calls = self._parse_tool_calls(resp.choices[0].message)
```

- `settings.max_iterations` 默认 8；耗尽时按是否有成功工具给兜底文案（`agent.py:217-221`）。
- `execute_tool` 第三参数 `{user_id, session_id, location, shop_id}` 是**用户隔离与店铺锁定的注入点**。
- `_post_process`（`agent.py:269`）：阶段推导 `_derive_focus`；UI/数据推导 `_derive_ui`（从最近一次成功工具**回溯**，跳过 `save_memory` 等辅助工具，避免卡片被"最后一个工具"覆盖）；幻觉校验 `_validate_respond_data`（如 `plan_card` 无 `plans` 则丢弃 data，改由真实工具结果重建）；QA 轮次丢弃擅自推送的方案卡；生图补调；markdown 清洗。
- 产物：写回 `messages`、更新 `sessions.stage`、组装 `ChatResponse`（`ui/data/action/products`，`ui_protocol.py:58`）。

## 5. 多平台接入与 `user_id` 派生

| 端点 | 适用 | 凭证 |
|---|---|---|
| `POST /auth/token` | H5/App/小程序自有后端（推荐） | 头 `X-API-Key` + 体 `external_user_id` |
| `POST /auth/wx-login` | 直接用微信 `code` | 需 `WECHAT_APPID/SECRET` |
| `POST /auth/anonymous` | ⛔ 仅开发联调 | 生产未显式开启即 403 |

```python
# backend/auth.py:136 derive_platform_user_id(platform_id, external_user_id)
safe   = ''.join(c if c.isalnum() or c in {'_','-'} else '_' for c in platform_id)[:32]
digest = hashlib.sha256(f'{platform_id}:{external_user_id}'.encode()).hexdigest()[:24]
return f'{safe}_{digest}'          # 例：wxmini_241f6dc5593f5051c7bf96ed
```

微信登录同理取 `openid` 的 sha256 前 24 位（`auth.py:166`）——**原始 openid/手机号/第三方 ID 不落库**，密钥轮换不影响 `user_id` 稳定性。归属校验 `require_user`（`auth.py:87`）：`AUTH_REQUIRED` 开启时 JWT 的 `sub` 与请求体 `user_id` 不一致直接 **403**；会话/任务层还有二次校验（`chat.py:71-74`、`memory.py:25`、`tasks.py:215`）。

## 6. 会话与记忆

- **短期**：`sessions` + `messages`。`load_history(sid, settings.history_limit)` 默认 20 条（`agent.py:173`），落库跳过 `role='tool'`（`memory.py:168`）。**多轮靠 `session_id` 回传**：不传 = 每轮新会话 = 用户感觉"失忆"，宿主必须持久化。
- **长期**：`user_preferences` → 注入 system prompt「用户偏好记忆」段（`agent.py:535-537`）。
- **会话级临时状态**：`memories` 表，`category` 用 `<session_id>` 或 `flag:<session_id>` 隔离（`memory.py:127-154`），承载 `latest_diy_plan`、`image_confirmed` 等——**替代旧版进程级全局变量，杜绝多用户串号**。
- **阶段**：`sessions.stage` 仅作 UI 焦点；上一轮 `DONE` 且本轮非寒暄时自动开新会话（`agent.py:158-160`）。

## 7. 店铺锁定模式的四层贯通

用户从某店铺页进入时 `/chat` 带 `shop_id`，此后整个会话只服务这家店。四层缺一不可：

| 层 | 位置 | 作用 |
|---|---|---|
| ① 入参 | `chat.py:40,75,79` | `ChatRequest.shop_id` → 建会话写入 `sessions.shop_id` |
| ② 持久化 | `memory.py:28,74`；`agent.py:153-156` | 后续轮次从会话读回，**会话内不可变** |
| ③ 工具上下文 | `agent.py:203` → `toolkit.py:78` → `data_tools.py:45`、`diy_tools.py` | 工具内 `_context['shop_id']` 兜底，LLM 漏传也不漏出跨店数据；显式传别的店直接报错（`data_tools.py:48-49`） |
| ④ 提示词 + SQL | `agent.py:538-547`；`external.py:353-356` | system prompt 加「店铺锁定模式」段（禁止查/推别家店）；SQL 层 `WHERE shop_id = %s` 硬过滤 |
补充：映射缺 `shop_id` 列时 SQL 无法过滤，工具返回 `meta.filtered_by='none_needs_model_filter'`（`data_tools.py:59`），要求模型按行内字段自行筛选。

## 8. 生图与贺卡：两套完全不同的机制

| | 效果图（花束预览） | 电子贺卡 |
|---|---|---|
| 工具 | `generate_effect_image`（`agent/tools.py:81`） | `render_greeting_card`（`skill_greeting.py:567`） |
| 实现 | 百炼 `qwen-image-3.0`，**异步** | Pillow 模板合成（文字清晰），**同步** |
| 返回 | `{task_id, poll}` → 轮询 `GET /tasks/{task_id}` | 直接 `{image_url, text, recipient, sender, template, note}` |
| UI | `image_task` | `greeting_card` |
| 耗时 | 数十秒 | 秒级 |

**生图链路**：

```
generate_effect_image('latest_diy') → _resolve_session_plan()（取会话 latest_diy_plan.effect_prompt）
  → tasks.create_image_task(prompt, user_id)          # tasks.py:192
       INSERT image_tasks(status='processing') + asyncio.create_task(_generate_image_async)
       立即返回 task_id（不等结果）
  → _generate_image_async()                            # tasks.py:179
       _generate_with_qwen() → _assert_public_image_url()（SSRF）→ 体积校验
       → save_generated('{task_id}.png') → UPDATE status='done'
前端 GET /tasks/{task_id}（chat.py:181）→ {status, result_url}
```

- **必须立即下载转存**：百炼返回带签名、有 `Expires` 的 OSS 临时地址，直接存 URL 会过期 403。
- 尺寸格式是 **`"768*1024"`（星号）**；OpenAI 兼容的 `/images/generations` 对 `qwen-image` 返回 **404**（`tasks.py:122-149`）。
- 重启兜底：`recover_incomplete_tasks()`（`tasks.py:56`）把残留 `processing` 置 `failed`；轮询按 `user_id` 归属过滤（`tasks.py:212-224`）。
- `IMAGE_PUBLIC_BASE_URL` 为空时 `result_url` 是相对路径 `/generated/xxx.png`，宿主前端需自行拼域名前缀。

**贺卡**：模板 `warm/blush/green/letter/night`，画布 `900×1200`（`config.py:85-86`），产物 `data/generated/greet_{ts}_{rand}.png`，落款已去品牌化。**不要用生图工具做贺卡**（模板合成文字才可辨认），system prompt 已约束（`agent.py:497`）。

## 9. LLM provider 链

`engine/llm.py:41` `_providers()` 返回 `[primary, *extras]`：

1. **primary**：`LLM_BASE_URL` + `LLM_API_KEY` + `LLM_MODEL`（生产为百炼 DashScope `https://dashscope.aliyuncs.com/compatible-mode/v1` + `qwen3.8-flash`）。
2. **hy**：仅 `HY_API_KEY` 非空时追加（历史腾讯通道，现为**可选 fallback**）。
3. **extra**：`llm_providers` JSON（当前 `settings.llm_providers` 恒返回空串，未启用）。

每个 provider 独立熔断器（`circuit_breaker.py`）；可重试错误（超时/5xx/429）指数退避重试，不可重试错误（4xx）立即切下一个；全部失败抛 `LLMUnavailableError`。
> `qwen3.8-flash` **带推理/思考**，响应含 `reasoning_content`，会先消耗 `max_tokens`——故 `LLM_MAX_TOKENS` 默认放宽到 3000（`config.py:188-190`），调小会导致 `content` 为空。

## 10. 关键设计决策与权衡

| 决策 | 替代方案 | 为什么这样定 | 代价 / 注意 |
|---|---|---|---|
| **① 平台只读架构**：本地不镜像商品/订单，实时只读查平台库 | 定时同步商品到内部 PG | 镜像空表会误导 LLM 返回空结果；同步带来一致性与合规负担 | 查询依赖平台库可用性；已删旧 `db_auto_*` 与 `gateway.py`（`mapper.py:11-14`） |
| **② 智能体不直接下单**：推荐结构化商品 → 用户点小程序卡片进宿主结算页 | 智能体调平台下单 API 直写订单 | 支付/分账/配送/售后应复用宿主既有逻辑；智能体不应持有下单权 | `create_order` 保留但策略上不调用；`PLATFORM_ORDER_API_URL` 未配即明确报错，不静默 |
| **③ 店铺锁定模式**：`/chat` 带 `shop_id` 锁定唯一商家 | 每轮让模型自己选店 | 用户已在某店内，再推别家是体验事故 | 需四层同时生效；映射缺 `shop_id` 列时退化为"模型自行筛选"，有漏出风险 |
| **④ 电子贺卡用 Pillow 模板合成、同步返回** | 用生图模型出贺卡图 | 生图模型写中文会糊/错字，贺卡核心是文字 | 模板固定 5 套，个性化上限受约束 |
| **⑤ `run()` 放线程池 + 独立事件循环** | 全链路 async 重写 | 存储层是同步 psycopg，改造面大风险高 | 牺牲 ContextVar 传递；埋点必须显式传 `cid`；真流式改造受阻 |
| **⑥ 对外自称统一「你的专属花艺小助手」** | — | 品牌由宿主决定，智能体不占位 | 仓库内仍有旧内部代号（FastAPI title / 启动日志 / 容器名），仅内部可见，待清理 |
| **⑦ SQL 用 `?` 占位符，适配器转 `%s`** | 直接写 `%s` | 保持仓储代码可迁移 | 正则 `(?<!%)\?`（`db.py:86`）；**同一条 SQL 不要混用两种占位符** |
