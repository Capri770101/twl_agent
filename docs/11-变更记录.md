## 2. 架构决策记录（ADR）

### ADR-1 · 平台只读架构（118c908）
- **决策**：智能体不镜像商品/订单；一律通过 `platform_db_query_entity(source_id, entity=plan|shop|order|user)` 实时只读查平台库（`PLATFORM_DB_<SOURCE_ID>_URL` 注入，`external.py` 强制 `READ ONLY`）。
- **理由**：避免双写与一致性风险；平台数据主权归平台方。
- **状态**：已落地，勿回退。

### ADR-2 · 智能体不直接下单（2026-09-05 反转）
- **决策**：`create_order` 从 `TOOL_REGISTRY` 移除（函数体保留）。改为「推荐结构化商品 reply+products → 用户点小程序商品卡片进现有结算页」。
- **理由**：直连下单需客户微信令牌/地址，易错单重单。恢复方向是新增 UI 动作 `open_checkout`，不是直连下单。
- **约束**：切勿配置 `PLATFORM_ORDER_API_URL`。
- **状态**：已落地，勿回退。（注：当前 `agent/` 中 `create_order` 装饰器调用仍在源码，属待清理项，见 K 系列。）

### ADR-3 · AI 电子贺卡（d52fc2b）
- **决策**：`agent/skills/skill_greeting.py` PIL 模板合成（warm/blush/green/letter/night，900×1200），契约 `GreetingCard{image_url,text,recipient,sender,template,note}`，UIType.GREETING_CARD。
- **约定**：`sender` 用用户昵称/自选文案（不塞 raw user_id）；底部水印固定「以花传情」。下单成功后 LLM 主动引导。

### ADR-4 · 店铺锁定模式（d708b33）
- **决策**：`/chat` 带 `shop_id` → 锁定唯一商家，四层贯通。缺货只给本店替代。
- **约束**：平台 mapping 必须含标准 `shop_id` 列，否则只能模型自筛。

### ADR-5 · LLM 选型：阿里云百炼 Qwen（2026-09-07）
- **决策**：provider = 阿里云百炼 DashScope。
  - 对话：`LLM_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1`，`LLM_MODEL=qwen3.8-flash`（带推理，响应含 `reasoning_content`）。
  - 生图：`IMAGE_PROVIDER=qwen`，`IMAGE_MODEL=qwen-image-3.0`，原生 `multimodal-generation` 接口（OpenAI 兼容 `/images/generations` 实测 404）。
- **理由**：原腾讯 hy 免费额度耗尽（402）且限流（429），切换后直连 qwen3.8-flash、延迟从 134s 降到 ~4.5s（首字 ~15s，含思考）。
- **风险/权衡**：qwen3.8-flash 带推理 → 比非思考模型慢；hy 仍作为 fallback 挂在 provider 链后，跨厂商兜底可能致风格跳变（如需纯 Qwen 清空 `HY_API_KEY`）。
- **状态**：已落地。

### ADR-6 · 对外自称与品牌隔离（2026-09-05）
- **决策**：运行时统一自称「你的专属花艺小助手」；仓库/文档里的历史项目代号（旧称「跳舞兰」）仅用于内部资产标识（容器名、域名、日志前缀），不是对外品牌名。
- **贺卡落款**：`sender` 用用户昵称/自选文案；水印固定「以花传情」。

### ADR-7 · 平台只读 REST 数据源（fe4af29，2026-09-15）
- **决策**：在「直连平台只读库」之外新增**只读 REST** 作为第二数据来源（`PLATFORM_API_<SOURCE_ID>_URL`，+可选 `_TOKEN`），**DB 优先**；适配层 `backend/data_gateway/http_source.py`。
- **理由**：平台只读库连接串长期不到位（T-4 阻塞），REST 立即可用，解除硬阻断。
- **边界**：仍属 ADR-1 的只读架构——不落库、不镜像、只查。⚠️ 该平台 **HTTP 恒 200，业务码在 body 的 `code`**；`price` 单位是**分**；匿名可读 products/shops/categories/banners。
- **状态**：已落地（生产当前走此通路）。

### ADR-8 · 客户体验演示栈物理隔离（bee304d，2026-09-16）
- **决策**：演示环境用**独立容器 + 独立库 + 独立密钥**（compose profile `demo`：`postgres-demo` / `agent-demo`），与生产完全隔离；能力范围收窄用 `PLATFORM_ALLOWED_ENTITIES`（演示设 `plan` = 只做方案与建议），**四层一起收口**（schema / 执行 / prompt / 卡片），配置写错时 **fail-closed**。
- **理由**：客户体验要用真实数据，但绝不能碰生产库；且演示**不要店铺推荐与下单链路**。
- **状态**：已落地。生产环境变量留空 = 不限制，行为零变化。

### ADR-9 · 理解主导，关键词仅兜底（8ef67ae，2026-09-16）
- **决策**：需求抽取（收花人 / 场合 / 风格 / 氛围 / 颜色 / 场景 / 预算）**以 LLM 理解为准**，正则只在模型没读到该字段时兜底；**精确字段（单一花材、支数）仍以规则为准**——那是用户明确说出的强约束，不该被模型转述覆盖。
- **理由**：原实现「只补空、绝不覆盖」→ 正则先抽到的值会锁死，模型读懂了也改不了；而「手头不宽裕」这类口语，正则根本抽不出任何数字。
- **同批**：出卡护栏判定也从「用户话里的关键词」转向「模型的实际输出」。
- **状态**：已落地。

### ADR-10 · 会话阶段必须反映事实（0098ba6，2026-09-16）
- **决策**：会话阶段（如 `IMAGE_GEN`）只在**事实成立时**保持，任务完成即退出；阶段不得演变成「话题锁定」。
- **理由**：`IMAGE_GEN` 曾永不退出，导致每轮都往 prompt 注入「图正在生成中」→ 用户问数据库信息却被当成生图话题回答（答非所问）。
- **同批**：护栏误判修复（普通「我生成了方案」被判成谎称出图）、重复生图修复。
- **状态**：已落地。

### ADR-11 · nginx 上游必须用变量式 proxy_pass（2920f45，2026-09-17）
- **决策**：`location` 的上游一律写成 `set $be http://agent:8000; proxy_pass $be;`（每次请求重新解析）。
- **理由**：静态 `proxy_pass http://agent:8000` 只在 nginx **启动时**解析一次并**永久缓存 IP**；容器重建换 IP 后会**静默打到别的实例**。真实事故：生产 `/auth/token` 全部 401、报「平台凭证无效」，实际是请求跑进了演示容器（演示 key 不匹配）——表现为「API key 失效」。
- **配套**：改 `deploy/nginx.conf` 后必须 `docker restart flora-nginx`（单文件 bind mount 换 inode，`reload` 无效）；`if` 必须写在 `rewrite ... break` 之前。
- **状态**：已落地，并用「强制换 IP 且不重启 nginx」验证通过。

### ADR-12 · 成交优先的推荐顺序（672504b，2026-09-18）
- **决策**：用户表达需求后**先看平台上有没有符合的现成品**——有就优先推（有实拍图、价格明确、能直接下单）；没有 / 用户明确要定制，才走 DIY。判定「有没有符合的」看**硬约束**（色系 / 主花材 / 场合 / 预算区间），**名称不完全一样不算没有**。
- **配套**：推荐现成品时要在回复里点明「点卡片可直接下单」；**DIY 不得承诺线上直接下单**（平台无对应 SKU），应如实说明需与店家沟通制作，并顺势推荐接近的现成款。
- **理由**：Capri 明确产品主线 = 快速定位需求 → 有成品推成品 → 没有才定制 → 引导支付。实测修复前「送女朋友生日花，预算300」直奔 DIY，**查了 4 次平台却只回一个买不到的方案**。
- **状态**：已落地。⚠️ 遗留：DIY 的真正线上成交仍需平台方提供「定制需求单」写入通道；平台是否具备该接口**无法匿名探测**（非公开路径一律 401，连不存在的路径也是 401）。
